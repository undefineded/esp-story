# Video V2 实现方案

## 目标与边界

在现有 ESP32-S3、320×240 ST7789 SPI 屏、1-bit SDMMC 硬件上，优先实现稳定 15～20fps 的视频播放。目标档位为 20fps，保底档位为 15fps；文件体积与格式通用性排在流畅度之后。

本方案是待实现的设计，不代表现有固件已经支持，也不保证任意素材都能达到目标。第一阶段保留现有硬件接线，以真机测试决定后续优化。

采用离线 RGB565 分块差分格式：电脑完成缩放、颜色转换和变化区域计算，设备完成顺序读取、更新画面和推屏。当前 QOI/MJPEG 播放链路保留作为对照与回退。

## 总体链路

```text
MP4 / MOV / MKV 等源文件
        │
        ▼ ffmpeg：固定帧率、缩放补边、转换 RGB565
RGB565 原始帧流 ──► 专用打包工具 ──► 同名 .sv2 视频文件
        源文件 ──► ffmpeg 提取音轨 ──► 同名 .mp3 音频文件

SD 卡顺序预读 → PSRAM 队列 → 应用帧更新 → DMA 暂存缓冲 → SPI 屏幕
独立音频任务 → I2S 输出 → 为视频提供播放时间基准
```

`.sv2` 是本项目拟定的自定义扩展名。ffmpeg 不能直接生成该格式，需要新增打包工具与固件解析器。

## 离线转码

### ffmpeg 生成原始帧

```bash
ffmpeg -i input.mp4 -an \
  -vf "fps=20,scale=320:240:force_original_aspect_ratio=decrease,pad=320:240:(ow-iw)/2:(oh-ih)/2" \
  -pix_fmt rgb565be -f rawvideo frames.rgb565
```

- 输出为固定 20fps、320×240，每帧 153600 字节。
- `rgb565be` 暂定对应现有画布的交换字节序存储；实现前必须用红、绿、蓝测试图确认整条链路的颜色及字节序。
- 15fps 档位将 `fps=20` 改为 `fps=15`。
- 工具正式实现时优先通过管道逐帧读取 ffmpeg 输出，避免保存巨大的中间文件。
- 默认保持比例并补黑边；可另提供裁切填满选项。

### 提取音轨

```bash
ffmpeg -i input.mp4 -vn \
  -ac 1 -ar 22050 -c:a libmp3lame -b:a 48k input.mp3
```

无音轨的视频不生成 MP3，使用单调时钟播放。转码工具必须保持音视频起点一致，处理源文件时间戳偏移，并清除可能遗留的同名旧音轨。

### 专用打包工具

新增 Node.js 工具，逐帧执行：

1. 第一帧输出完整关键帧。
2. 将当前帧与前一帧按 16×16 像素块比较，边缘块按实际尺寸处理。
3. 记录发生变化的块，保存该区域最终的 RGB565 像素，不使用 XOR 数据。
4. 合并相邻块为矩形，控制矩形数量与命令开销；合并策略以真机总耗时为依据。
5. 若差分记录总长度不小于完整帧记录，改存完整关键帧。
6. 默认每 1 秒插入关键帧；完全相同的画面保存空更新帧，仍占一个时间位置。
7. 写入帧索引和统计信息，并重新解析产物校验。

第一版不启用压缩。后续仅在实测证明读取收益超过解压开销时增加 LZ4，不能假设无压缩一定最快。

## 文件格式草案

元数据统一使用小端整数，像素字节序由文件头明确标记。禁止直接把 C++ 结构体内存当作文件格式，避免对齐与平台差异。

| 层级 | 内容 |
| --- | --- |
| 文件头 | magic、版本、头长度、宽高、像素格式、帧率分子/分母、帧数、最大记录长度、索引偏移 |
| 帧记录头 | 记录长度、帧序号、帧类型、矩形数量、校验值 |
| 关键帧 | 完整 RGB565 像素 |
| 差分帧 | 矩形列表，每项含 x/y/w/h、数据长度及逐行紧密排列的像素 |
| 空更新帧 | 无像素载荷，只推进时间位置 |
| 索引 | 每帧偏移、记录长度、帧类型；支持定位关键帧 |

具体字段宽度、校验算法和 magic 在实现时固化为版本 1，并由工具和固件共用格式说明。偏移建议使用 64 位，避免格式被 4GB 上限限制；固件文件接口的实际能力另行验证，必要时由转码工具分片。

矩形必须在画面范围内，像素数据长度必须等于 `w × h × 2`。限制单帧矩形数、最大记录长度与索引内存，所有长度和偏移计算检查溢出。格式不沿用旧播放器固定 8000 帧的限制，长片采用分段索引或按需读取。

## 固件播放流程

### 顺序预读

- 使用一个视频文件读取任务，顺序大块读取到有界 PSRAM 队列。
- 队列按字节容量限制，依据剩余 PSRAM 分配，不固定假设每帧同样大小。
- 起播前积累一定数据；初始可尝试数百毫秒预读，并按实际内存和延迟调整。
- 视频与音频仍共用 SD 卡，避免一次长读独占卡片导致音频欠载；读取块大小通过并发测试确定。

### 应用差分与提交画面

- PSRAM 保留完整 RGB565 视频画面，将关键帧或差分矩形写入该画面。
- 正常播放直接使用文件中的变化区域，无需重新比较整屏像素。
- 使用两个内部 RAM DMA 暂存缓冲，发送一个时准备另一个；只有复用仍被 DMA 占用的缓冲时才等待。
- 两个 DMA 缓冲不等于两幅完整画面，不预设内部 RAM 能容纳完整帧。
- 显示 API 的异步行为、缓冲生命周期和跨任务调用限制必须先验证；同一 SPI 屏由单一任务管理。
- 首版可先串行验证格式正确，再引入并行流水线，分别测量收益。

### 丢帧规则

差分帧依赖此前画面，不能像 QOI 独立帧一样直接跳过中间记录。

- 轻微落后：依次应用中间差分，只省略中间画面的推屏。
- 省略推屏时，累计所有尚未提交的脏区域；不能仅发送最后一帧的变化区域。
- 严重落后：定位到合适关键帧，重建画面后恢复播放。关键帧落在当前时间之后时，应等待对应时间或选择前一个关键帧重放，避免画面提前。
- 损坏差分记录后不能继续沿用失效画面，应恢复到可验证的关键帧，或报告错误并停止。

### 音画同步

- 有音轨时，以实际输出的音频采样数换算播放时间；文件已连接不等于已出声。
- 需要扩展当前音频封装，确认解码库与 I2S 能否提供输出采样进度，并处理 DMA 中尚未播放的数据。
- 如果第一阶段只能取得粗粒度播放时间，应明确其误差，使用单调时钟配合音频起播确认及渐进校正，不宣称采样级同步。
- 暂停、恢复和换片使用明确状态及确认，避免视频已暂停而音频命令仍在队列中。
- 无音轨时使用单调时钟。帧时间按帧率分数计算，避免长期累积舍入误差。

### 控制条与 UI

视频底图与 UI 叠加分离。控制条出现、变化或消失时，把对应区域加入脏区域；隐藏时从视频底图恢复，即使源视频该区域没有变化也必须刷新。

视频调度独立于当前通用 UI 的 33ms 提交限制。实际帧率只统计成功提交的不同视频帧，另记跳过显示的帧、失败帧与音频欠载。

## 带宽和性能预算

320×240 RGB565 完整画面为 153600 字节：

| 项目 | 15fps | 20fps |
| --- | ---: | ---: |
| 单帧时间预算 | 66.67ms | 50ms |
| 无压缩整帧视频读取量 | 2.304MB/s | 3.072MB/s |
| 假设仅 25% 像素变化时的载荷读取量 | 约 0.576MB/s | 约 0.768MB/s |

差分数据另有矩形、索引及关键帧开销，25% 只是示例，不是素材保证。

40MHz SPI 发送整屏像素理论需要 30.72ms，80MHz 为 15.36ms，实际还有复制、命令和调度开销。优先验证 40MHz 能否满足目标，必要时测试 80MHz 的信号稳定性。

全屏运动、噪声和频繁切镜会使差分退化为整帧，当前 1-bit SD 的实际速度可能无法持续承载。因此转码报告必须列出平均及峰值读取量、关键帧大小和变化比例；不能只凭平均值承诺稳定 20fps。

## 实施顺序

1. 为当前播放器记录读卡、解码、推屏、帧间隔及音画偏差，建立 15/20fps 对照数据。
2. 固化版本 1 文件格式，实现打包、解析和主机端逐帧像素校验。
3. 实现固件串行播放，验证关键帧、差分帧、空帧和 UI 恢复。
4. 加入有界预读、两个 DMA 暂存缓冲及脏区域累计，测量并行收益。
5. 完善音频起播确认、时间校准和暂停恢复。
6. 根据数据决定是否提高 SPI 时钟、增加 LZ4 或提供不同素材档位。

## 验收

- 主机端将打包文件逐帧恢复，与 ffmpeg 输出的 RGB565 原始帧逐像素一致。
- 覆盖静态画面、局部运动、全屏平移、频繁切镜、复杂纹理及带音轨长片。
- 20fps 档位重点检查实际显示帧间隔：报告 P50/P95/P99、最大间隔、丢帧率与音画偏差，不能只报告平均 FPS。
- 连续播放至少 30 分钟，检查音频欠载、持续漂移、内存变化、卡顿和复位；具体通过阈值在基线实测后固化。
- 验证暂停恢复、换片、控制条隐藏、文件截断、错误长度、CRC 错误和读卡失败。
- 对相同素材比较当前 QOI 方案；若复杂素材持续达不到目标，依据读卡与推屏数据决定压缩或硬件调整。
