# 音频/视频卡顿排查记录

2026-11-05/06 两轮排查的现场记录。两次症状相似（间歇断音），根因同源：**一次写入的块大于 I2S DMA 环**。保留过程是因为中间的误判和排除项对后续调参同样有用。

## 一、音乐播放间歇卡顿

### 症状

音乐每几百毫秒出现一次可闻断点；视频不受影响。

### 测量手段

1. **开机自测**（不依赖按键）：解码一个 MP3 并按 I2S 实时节奏喂数，统计 `writes / gap_max / dec_max / rate`。没有 UI 干扰，能单独判断"生产端够不够快"。
2. **播放期 3 秒汇总**：`rate`（实际送样率）、`dec_max`（解码+读卡最坏耗时）、`wr_max`（I2S 写入最坏阻塞）、`gap_max`（两次写入间最大空档）、`yields`（主动让出次数）。

### 现场数据

| 指标 | 数值 | 解读 |
|---|---|---|
| `rate` | 41 859 / 44 100 | 持续 −5% |
| `gap_max` | 20–29 ms | 每帧都有空档 |
| `dec_max` | 23–33 ms | 接近一帧时长 |
| `yields` | 0 | 新的让出策略没参与 |
| 卡速（4 KB 读） | 20 ms / 4 KB ≈ 145–200 KB/s | 一度以为卡是瓶颈 |

### 排除项

- **不是 SD 带宽**：128 kbps 只要 16 KB/s，卡实测 145–700 KB/s（见"读数陷阱"）。
- **不是编译器优化**：`-Og` 换 `-O2`，`dec_max` 不变。
- **不是新的让出策略**：`yields=0`，RunBudget 从未触发。

### 根因

DMA 环 **4×240 = 960 帧（21.8 ms）**，而每次写入是完整的 MP3 帧 **1152 帧（26.1 ms）**。块比环大，`i2s_channel_write` 每次必须等这 1152 帧几乎放完才返回，**解码时间无法与播放重叠**，于是每帧固定损失约 2 ms，稳定 −5~8%。

自测佐证：同一循环在 960 帧环下只有 40 411 帧/s；把环加到 3 840 帧后变成 48 723 帧/s（高于实时）。

### 修复

- 写入按 **480 帧（一个 DMA 描述符）分片**，调用方传多大块都不再强耦合（照 xiaozhi 音频输出的做法：每片一个描述符 + 写入预算）。
- 音乐环改为 **8×480 = 87 ms**，覆盖曲目起播时的页面重绘突发。
- 解码结束的排空等待按真实 `capacity()` 计算，不再写死 960 帧。
- 视频路径保持较小的环（见下文）。

### 验证

```
rate=44100/44100  gap_max=22ms  stalls=0  yields=10~70
```

## 二、视频音频间歇卡顿

### 症状

画面 FPS 稳定（14–15），内嵌音频仍间歇断。

### 现场数据

```
video-audio: rate=40500/44100  gap_max=14~21ms  stalls=0
VIDEO_RENDER: Write too slow reset rate control   （偶发）
```

### 排除项（依次）

| 假设 | 验证 | 结论 |
|---|---|---|
| 卡带宽不够 | 64 KB 块实测 **698 KB/s**，素材 158 KB/s | 排除 |
| 帧邮箱锁竞争 | 三缓冲改造后 `copy_max=0ms` | 排除 |
| 任务布局不对 | 改用官方默认（音频解码回 core 1） | 无改善，排除 |
| 渲染 fps 与实际不符 | `fps=15` 与流一致 | 排除 |

### 决定性数据

每次 `writeAudio` 收到的都是 **17 640 B = 4 410 帧 = 100 ms** 整块，而每次调用耗时约 **97 ms**。组件里 `ESP_PLAYER_AUDIO_RENDER_FRAME_MS = ESP_PLAYER_AUDIO_RB_TIME_MS >> 2`，即 esp_player 固定按 100 ms 交付 PCM。

计算：帧周期需要 100 ms，实际 108.8 ms（97 ms 阻塞 + 8.8 ms 块间间隔），
`44 100 × 100/108.8 = 40 500` —— 与实测完全一致。

### 根因

与音乐同一个结构性错误：**块（100 ms）> 环（33 ms）**。每次写入为整块让路，块间开销变成永久赤字。

### 修复

视频环 **12×480 = 130 ms**（能装下一整块 100 ms），写入随环排空返回，周期回到渲染器自己的 100 ms。

### 验证

```
43 773 / 44 531 / 44 037 / 44 100 / 44 316  （连续 3 秒窗口）
```

播放期出现的 ~80 ms 写入耗时是**正常背压**（环满等播放），不再代表欠载。

### 已知代价与后续

- 音频缓冲加深约 100 ms，理论上画面可能比声音领先。若上板听感不符，改为**独立供数任务 + 内存抖动缓冲**：100 ms 块快速收进内存环，由单独任务按 480 帧喂 I2S，既不断音也不加 DMA 延迟。
- 素材码率仍需 ≤100 KB/s（慢卡），工具已会打印并在超标时警告。

## 排查方法（可复用）

1. **先量，再改**：开机自测 + 3 秒周期计数，比逐次猜参快得多。
2. 判定规则：
   - `rate < 采样率` → 生产端持续不足；
   - `gap > 环深` → 必然断音；
   - `copy_max` 大 → 锁竞争；
   - `dec_max` 尖峰 → 读卡/解码慢；
   - `wr_max ≈ 超时值` → 写入在等环。
3. **读数陷阱**：小读块会严重低估卡速——4 KB 读只有 ~145 KB/s，64 KB 读有 **698 KB/s**。测卡速务必用 ≥64 KB 块。
4. **块与环**：任何 `i2s_channel_write`/DMA 环，环深必须大于单次最大块 + 抖动余量；否则吞吐会稳定损失"块间开销/块时长"。

## 走错的弯路（按顺序）

1. 怀疑 `-Og` 太慢 → 换 `-O2`，无改善。
2. 怀疑 1-bit TF 卡带宽 → 实测 700 KB/s，够用。
3. 怀疑帧邮箱锁竞争 → 三缓冲后 `copy_max=0`，rate 仍是 40.5k。
4. 怀疑任务核绑定 → 切官方默认，rate 不变。
5. 最后回到**块大小 vs 缓冲深度**，两次都是同一个问题。

教训：看起来像"带宽/CPU/调度"的间歇断音，先核对"喂数据的块"和"缓冲能装多少"，这两项一比就能算出吞吐上限。
