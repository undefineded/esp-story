## BLE 目录同步（本轮已改，待真机计时）

现象：TF 卡里的歌越多，小程序连接后的「数据同步中」越久。

原因：目录是 `get what=music|stories|cats` 一页一页拉下来的，固件把每页死死限制在 4 条，
小程序又严格串行 —— 每页要一次完整往返（写请求 → 设备组 JSON → 十几条 notify → 微信
JS 桥逐个回调）。N 首歌就是 N/4 次往返：110 首约 28 次，300 首上限约 75 次。这条成本
随卡内容线性增长，而且任何一页丢一个分片就整份同步失败（旧代码连重试都没有）。

改动：

- 分页上限 4 → 24（`kListPageMax`，小程序按协商 MTU 选 24/12/4），单页响应可达数 KiB。
- `sendDoc` 不再用 1024B 栈缓冲，改为按实际长度堆分配后按 MTU 分片；分片失败仍保留重试。
- 新增内容版本号 `rev`（曲目/故事名 + 分类 + 内容白名单掩码的 FNV-1a）：
  - `hello` 回包带 `rev`；
  - 新增 `get what=meta`，回 `{rev,tracks,stories,cats}`；
  - 每个列表页的 `data` 里也带 `rev`。
- 小程序按 `rev` 缓存整份目录（`storyCatalog:<deviceId>`）：版本一致就跳过列表下载，
  只在 `rev` 变化（加删歌、改白名单）或用户点「刷新状态」时整份重下。
- 分页响应期间暂停 1 Hz 的 `evt:state` 事件（1.2 s 静默窗口），避免两条流抢空口和丢分片。
- 单页请求失败重试一次，不再因为一个坏页放弃整份同步。
- 界面上把两种同步分开：目录同步只占「内容库」区域的一行提示（可继续点播放、切 tab、返回），
  全局 loading 只留给连接和「刷新状态」里的状态/配置读取。

效果（估算，代码级）：首次同步往返次数降到 1/6；内容没变时的重复同步从几十次往返降到 1 次
（`meta`）。卡越大，收益越大。

## 本轮交付记录

- H1：单控制任务独占官方播放器，最新请求覆盖旧请求，旧完成消息不能覆盖新状态；音乐/故事交接同样串行化。取消请求不等待，但官方阻塞调用返回前不能完成资源清理。
- H2：播放和上下个视频复用列表快照；返回列表按存储版本决定是否扫描。
- H3/H5：双暂存区交替准备与发送；视频整帧提交，退出视频后重新建立普通 UI 的差异比较镜像。
- H4：UI 借用有锁的最新帧直接画入画布，减少一次整帧复制并释放约 150 KiB 页面 PSRAM；增加约 5 KiB 内部 DMA 暂存和一个 8 KiB 控制任务栈。
- H6：新增 `sdkconfig.performance`，性能优化、保留断言，单独构建并检查 OTA 空间；不覆盖已有本地 sdkconfig。
- H7：按 I2S 背压及 4 ms 连续运行预算让出 CPU；新增纯解析长耗时、公平性和背压测试。
- H8：通过 USB 系统状态暴露各阶段耗时、首个后端画面、后端拷贝、LCD 实际提交次数/字节/耗时、普通音频解码/写入、控制任务栈余量。CPU 负载增加有效性标志；官方视频解码内部耗时、SD 独立延迟和双核实际负载仍需实机分析。
- 并发请求测试覆盖快速选择、取消、旧结果到达和 10000 次连续请求；最新帧访问及请求控制通过 ASan/UBSan 检查（未启用泄漏检测）。
- 默认与 USB＋OTA＋省电组合固件约 2.54/2.59 MiB；性能组合约 2.62 MiB。OTA 槽大小以当前分区表和构建输出为准。
- 验证边界：主机测试不能证明真实 SD、I2S、SPI DMA 时序、面板帧率、长时间音画同步或功耗。中低优先级项保留待办。
